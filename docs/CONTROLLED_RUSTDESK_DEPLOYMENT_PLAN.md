# RustDesk 受控一体化部署改造计划

## 目标

将当前 RustDesk API Server Pro 改造成类似 `lejianwen/rustdesk-api` 的受控部署模式，实现 `API + hbbs + hbbr` 一体化部署，并让 `hbbs/hbbr` 参与注册制和登录态校验，避免客户端绕过 API 直接连接。

目标状态：

- 使用一个 Docker 镜像或一套 Compose 启动 API、`hbbs`、`hbbr`。
- `hbbs` 不再裸放行设备连接。
- 设备连接前必须完成 API 登录、注册或审批校验。
- 后台禁用用户、禁用设备、撤销授权后，RustDesk 连接也会被拒绝或尽快失效。
- 保留当前后台、OAuth、用户管理、设备管理等能力。

## 基本判断

当前 API 服务不能替代 `hbbs/hbbr`。注册制要真正生效，准入控制必须落到 RustDesk 服务端链路上。

参考 `lejianwen/rustdesk-api` 时，需要明确一点：所谓“一个服务”不是没有 `hbbs/hbbr`，而是把 API、`hbbs`、`hbbr` 放进同一个部署单元，并配合改造版 RustDesk Server 的强制登录能力完成准入控制。

因此本项目的改造重点不是让 Go API 模拟 RustDesk 协议，而是：

- 当前 API 提供稳定的内部鉴权接口；
- 改造版 `hbbs/hbbr` 调用 API 做准入判断；
- Docker 部署层将三者组成一个受控服务单元；
- 网络和密钥策略防止继续使用裸 `hbbs/hbbr` 绕过注册制。

## 阶段 1：确定准入协议

### 任务

为 `hbbs/hbbr` 调用当前 API 设计内部接口。

计划接口：

- `POST /internal/rustdesk/auth`
- `POST /internal/rustdesk/device/register`
- `POST /internal/rustdesk/device/heartbeat`
- `POST /internal/rustdesk/relay/check`

### 约束

- 内部接口只允许容器内部、本机或可信网络访问。
- 内部接口必须使用内部密钥、HMAC 或等价机制保护。
- 所有错误消息必须带 `ERR-xxxx` 前缀。
- API 异常时默认拒绝新连接。
- 返回结构必须稳定，方便 RustDesk Server 侧解析。

### 建议返回结构

```json
{
  "allow": true,
  "user_id": 1,
  "device_id": "rustdesk-device-id",
  "policy": {
    "allow_relay": true,
    "expire_at": 1790000000
  }
}
```

### 拒绝示例

```json
{
  "allow": false,
  "code": "ERR2201",
  "message": "ERR2201 设备未注册或未授权"
}
```

### 产出

- 内部接口设计文档。
- 错误码列表。
- RustDesk Server 调用 API 的请求和响应样例。
